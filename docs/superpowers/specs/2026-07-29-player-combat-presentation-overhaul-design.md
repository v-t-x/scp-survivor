# SCP Survivor 玩家角色与战斗表现重制设计

## 1. 文档状态

- 日期：2026-07-29
- 当前阶段：Phase 0 书面设计已获项目所有者确认，外部评审“小修后批准”意见已纳入，Phase 1 实施计划等待最终授权
- 当前授权：只允许分析、设计与实施计划，不授权代码、素材、分支、worktree、commit、push、merge、Release 或部署
- 目标基线：`feature/ui-art-overhaul` 已提交状态 `2ae0385`
- 产品审查等级：Level 2
- 外部评审结论：`Approve with minor revisions`；Phase 1.5 接点验证、装备局部坐标、Equipment Presentation、光刃验证理由和玩家体验目标已纳入

本文定义 Player Overhaul 的产品定位、架构边界、素材路线、实施阶段和验收标准。它不授权立即重写现有系统，也不把未来光刃原型自动升级为正式玩法。

## 2. 最终产品定位

Player Overhaul 的目标不是把 SCP Survivor 改造成 Hades 式主动动作游戏。

目标方向是：

> Vampire Survivors 的核心循环 + Risk of Rain 的角色与装备身份 + Enter the Gungeon 的武器存在感 + Diablo 的俯视角重量与氛围 + SCP 基金会世界观。

游戏继续以自动攻击、升级构筑、六分钟生存和终局 Boss 为核心。Player Overhaul 只增强玩家角色、武器、攻击来源和异常装备的表现能力。

### 2.1 各参考作品的使用边界

- **Vampire Survivors**：继续作为核心玩法循环的权威参考，包括自动攻击、成长、构筑和生存压力。
- **Risk of Rain**：学习角色作为装备和能力平台的身份表达，不复制高操作密度。
- **Enter the Gungeon**：学习枪械方向、枪口、后坐力和射击可读性，不引入手动瞄准。
- **Diablo**：学习俯视角角色重量、装备层次和角色与环境的关系，不改造成刷装备 ARPG。
- **SCP 基金会**：决定异常装备必须具有规则、代价、风险和设施语义，不能只是更高伤害的换皮武器。

## 3. 玩家身份

玩家不是依赖复杂连招和英雄演出的动作角色，而是一名基金会特遣队员：

> 使用制式武器和异常装备，在设施收容事故中生存并完成再收容。

角色本体负责：

- 基金会身份和可辨识轮廓；
- 移动重量、脚底与接地感；
- 装备承载能力；
- 受击、冲刺和生存状态反馈。

武器与异常装备负责：

- 攻击身份和攻击方向；
- 枪口、放电端或近战作用点；
- 后坐力、攻击节奏和命中特效；
- 构筑与异常能力差异。

未来增加新装备时，应优先制作独立装备、连接规则和特效，不为每件武器重新生成一整套完整人物动画。

## 4. 保持不变的核心循环

以下内容不因 Player Overhaul 改变：

- 自动寻找目标和自动攻击；
- 三选一武器、升级和构筑；
- WASD 移动、闪避与拾取；
- 六分钟生存时间轴和设施干扰；
- SCP-049 终局 Boss；
- 当前伤害、刷怪、AI、升级概率、胜负和存档语义。

真实枪口迁移会造成局部攻击几何变化，必须在 Phase 3 作为明确例外单独批准和验收，不能伪装成纯美术修改。

## 5. 明确不做

本设计不包含：

- 手动普通攻击或手动瞄准；
- 连招、攻击取消或 Hades 式高密度操作；
- 依赖动画回调决定伤害的复杂角色状态机；
- 为手枪、霰弹枪和特斯拉分别制作三套完整人物动画；
- 角色选择、多角色技能、账号或新存档字段；
- 对六分钟结构、胜负条件、敌人 AI 或现有构筑系统的重写；
- 恢复已撤回的肩部悬浮武器、平滑延迟装具或独立背包炮塔；
- 以 Player Overhaul 为理由全面拆分 Gameplay Scene；
- 在本设计阶段把异常光刃加入正式武器池。

## 6. 已选架构：保留玩法锚点，新增可回退表现层

玩家由两层组成。

### 6.1 玩法层

现有玩家对象继续作为唯一玩法权威，负责：

- 世界坐标和移动速度；
- 24×24 Arcade Body；
- 碰撞、重叠和拾取；
- 敌人追踪目标；
- Camera Follow；
- 受伤、无敌、死亡和其他玩法状态。

现有玩法模块继续读取同一个玩家对象，不迁移到新的全能 `PlayerController`。

### 6.2 表现层

新增独立玩家表现控制器，负责：

- body-only 人物 Sprite；
- 独立手臂和武器；
- 动画、脚步、视觉起伏和倾斜；
- 受击、冲刺、透明度和表现反馈；
- 武器方向、枪口、后坐力和特效；
- 素材缺失、构造失败和重启时的完整回退。

表现层只能读取由玩法层提供的基础状态，不能写回玩家坐标、速度、碰撞体、目标、伤害、RNG 或存档。

### 6.3 为什么不采用其他方案

不采用 Phaser Container 作为主要角色结构，因为它不能替代现有物理玩家，并会增加子对象深度、受击染色、动画和 Arcade Body 对齐风险。

不采用完整 PlayerController/WeaponBase 重写，因为现有移动、敌人、武器、碰撞、拾取、镜头和 HUD 都直接依赖当前玩家对象。一次性迁移会把表现升级扩大成核心玩法重写，与更新后的产品定位冲突。

## 7. 玩家表现结构

玩家实际显示由以下部分构成：

```text
玩法玩家锚点（默认隐藏）
├── body-only 人物
├── 独立手臂与当前武器
├── 枪口或异常装备作用点
├── 受击、冲刺与开火表现
└── 接地阴影
```

玩法锚点先以安全旧资源创建。只有新表现完整构造成功后才隐藏锚点；任何构造、动画或资源失败都必须销毁半成品并恢复旧角色。

### 7.1 移动重量

移动重量只作用于可见人物：

- 脚底对应稳定的地面基线；
- 阴影固定在玩法锚点下方，不随身体上下跳动；
- 身体允许克制的上下和左右反馈；
- 移动速度影响动画节奏；
- 移动方向产生轻微倾斜；
- 停止后自然回到待机；
- 冲刺使用更明确的前倾和残影。

不得通过修改玩法玩家的位置、缩放、显示原点或碰撞体实现视觉重量。

## 8. 新 body-only 角色素材

现有未提交 Gate 3 候选把紧凑枪械画入人物帧，不能与独立武器层共存。该候选不再进入最终收尾，也不作为新系统 fallback。

新人物继续保留以下合同：

- 每帧 64×64 RGBA；
- `down / left / right / up` 四个真实方向；
- 每方向 30 帧；
- `idle / forward / backward / strafeLeft / strafeRight / hit` 六类动作；
- 总尺寸 1920×256，共 120 帧；
- 当前琥珀识别特征和基金会异常响应干员身份；
- 现有 24×24 碰撞体不随素材变化。

变化为：

- 人物帧中不得出现枪械、光刃或其他具体武器；
- 人物身体负责头部、躯干、腿部和装备主体；
- 肘部以下前臂、双手和武器作为独立武器组合；
- 每个动画帧登记稳定的上身连接位置和前后遮挡关系；
- 不为三种武器生产三套完整人物表。

旧带枪 Gate 3 候选只能作为身份、配色和失败经验参考，不得作为逐帧擦除枪械或直接转换 body-only 的生产源。

### 8.1 素材完整性

只有以下内容全部有效时才启用新版角色：

- body-only spritesheet；
- 动画注册；
- 每帧连接位置数据；
- 当前武器组件；
- 对应 fallback 和销毁路径。

任一部分缺失或错误时，整套回退，不能显示裸人物、空气武器、双武器或残留组件。

### 8.2 新视觉门

旧 Gate 3 不再延续为完成门。新素材使用独立门禁：

1. **Body Gate A**：单方向 body-only 身份与轮廓，确认零武器像素。
2. **Body Gate B**：单方向移动原型和连接位置，确认脚步、重量与武器不漂浮。
3. **Body Gate C**：完整四方向 120 帧、一个 Phase 1.5 dummy equipment、fallback 和真实游戏试玩。

前一门未明确接受时，不扩展下一门。

Body Gate B 只生产 `down` 方向的 idle、forward、backward、strafeLeft 和 strafeRight，共 28 个移动帧。该方向的风格、脚底、接地、移动重量和连接位置未接受前，不生成 left、right、up 或完整 120 帧。

### 8.3 120 帧是总预算，不是单动作预算

120 帧表示四个方向各 30 帧的完整总表，不表示每个动作都需要 30 帧。每个方向固定分配为：

- idle：4 帧；
- forward：6 帧；
- backward：6 帧；
- strafeLeft：6 帧；
- strafeRight：6 帧；
- hit：2 帧。

冲刺、后坐和轻微身体倾斜优先使用程序表现，不额外制造成套 dash 或 attack 帧。只有用户试玩证明现有预算无法表达必要动作时，才另行提出素材预算调整。

## 9. 身体方向与武器方向

身体方向由移动和冲刺决定：

- 玩家移动时，身体跟随移动方向；
- 停止时保持最后有效移动方向；
- 攻击不能强制旋转整个身体。

武器方向由自动攻击目标决定：

- 玩家可以向左撤退，同时向右开火；
- 武器在发现有效自动目标后立即指向目标；
- 不加入手动瞄准；
- 不使用旧肩部装置的平滑延迟、回正等待或漂浮偏移；
- 枪口、曳光和实际攻击使用精确攻击方向。

人物身体继续播放移动相关动作，不为每把武器增加完整攻击动画。

### 9.1 Equipment local coordinate

所有独立武器和异常装备使用同一局部坐标约定：

```text
装备默认前方 = local +X
rotation = 0 = 朝屏幕右侧
装备 pivot = 自身 grip socket
枪口、放电端或近战作用点 = 装备自身 local space
人物连接位置 = body frame local space
```

装备素材若原始方向不是朝右，必须在素材处理阶段统一到 `+X`，不得在各武器运行时代码里散落 `+90°`、`-90°` 或镜像补丁。

人物每帧只提供 grip、support 和前后遮挡信息；装备自己提供 pivot 和 action point。表现层可以把两者转换成画面位置，但 Phase 1/2 不得把计算出的枪口或作用点写回玩法层。

## 10. 三种现有装备的表现身份

本设计使用 **Equipment Presentation** 表示角色携带的攻击装备，不把接口限定为 `Weapon Sprite`。它可以表达枪械、手持异常设备和未来另行批准的其他装备形态，但 Phase 2 只实现当前手枪、霰弹枪和特斯拉设备，不提前建立背包、悬浮装置或肩部炮塔系统。

### 10.1 手枪

- 轻巧、快速、后坐较小；
- 清楚的单发枪口和弹道；
- 多弹升级仍属于同一次自动攻击；
- 武器表现不得改变弹数、角度或冷却。

### 10.2 霰弹枪

- 轮廓和重量明显高于手枪；
- 更强后坐和扇形枪口反馈；
- 空仓与换弹可从武器姿态辨认；
- 表现不得改变弹丸数、弹仓、换弹或 Boss 目标优先级。

### 10.3 特斯拉

- 作为异常电击设备表现，不伪装成普通枪械；
- 不强制复用手枪的枪管、弹仓、枪口或换弹表现合同；
- Phase 2 先采用手持异常设备形态，使用 grip/support 连接和独立放电端；
- 攻击方向由第一个有效目标决定；
- 电弧继续沿现有规则连接目标；
- 作用点位于设备放电端；
- 不生成没有玩法意义的装饰性子弹。

## 11. 攻击与表现的数据边界

攻击流程保持为：

```text
自动寻找目标
→ 玩法确认攻击
→ 创建弹丸或完成电击伤害
→ 发布只读攻击结果
→ 播放枪口、后坐力、曳光与命中特效
```

持续武器姿态只描述当前武器、自动目标方向、待机、瞄准、换弹或冷却。攻击结果只描述已经成功发生的攻击。

表现层不得决定：

- 是否攻击；
- 目标是谁；
- 是否命中；
- 伤害数值；
- 弹丸数量；
- 霰弹消耗与换弹；
- 冷却和攻击频率；
- 升级、击杀和奖励；
- 近战伤害窗口。

表现系统缺失、返回失败或抛错时，玩法结果必须完全一致，并保留可用的最低级反馈。

## 12. 真实枪口迁移

当前正式弹丸仍从玩家中心创建，已有枪口闪光只是视觉偏移。真正迁移到枪口会影响：

- 玩家身边的敌人是否被跳过；
- 最大射程端点；
- 穿透目标顺序；
- 霰弹命中分布；
- 回旋弹折返路径；
- 伤害来源方向与距离判定。

因此 Phase 3 必须把真实枪口作为单独 Level 2 子门：

1. 先保留中心弹道，完成独立武器和视觉枪口；
2. 再由玩法层计算真实攻击起点；
3. 表现层只读取玩法层确认的攻击起点并对齐画面；
4. 对近身、边界射程、穿透、霰弹、回旋弹、Boss 和方向伤害重新验收。

表现层不得把自己计算的枪口坐标返回给玩法层。

## 13. 异常光刃开发态验证

异常光刃只用于验证新框架是否支持非枪械装备。选择它不是为了扩充正式玩法，而是因为一个最小原型可以同时检验：

- 装备绕 pivot 旋转；
- 不依赖 projectile 的攻击表现；
- 空间作用范围；
- 命中反馈与挥砍轨迹；
- 攻击来源和作用点的表达。

如果这些能力能在不改变自动攻击核心的情况下自然工作，就说明框架可以承载未来异常装备；如果不能，应修正表现接口，而不是用更多数值或角色动画掩盖问题。

开发态原型包含：

- 自动寻找附近目标；
- 自动挥砍；
- 固定测试范围；
- 武器旋转和挥砍轨迹；
- 明确攻击作用点；
- 命中与异常特效；
- 暂停、受击、重启和 fallback。

开发态原型不包含：

- 手动攻击；
- 连招；
- 正式伤害平衡；
- 正式三选一入口；
- 升级池；
- 永久存档；
- 产品化许可。

验证通过只说明框架可以承载近战装备。是否将光刃做成正式自动攻击武器，需要新的玩法提案和批准。

## 14. 分阶段实施

### Phase 0：分析与设计

当前阶段。只完成仓库分析、产品定位、方案比较和书面规格，不修改代码或素材。

完成条件：

- 项目所有者接受书面设计；
- 决定是否进行外部 GPT 5.6 审查；
- 另行批准实施计划和隔离工作区。

### Phase 1：角色存在感

目标：

- 分离玩法锚点和可见人物；
- 完成 body-only Gate A/B/C；
- 建立脚底、阴影、移动重量、受击、冲刺和完整 fallback；
- 保持碰撞、移动和玩法语义不变。

本阶段不实现独立正式武器，也不改变弹丸起点。

Phase 1 完成后，body-only 人物、连接位置和 Phase 1.5 dummy equipment 只通过显式开发预览入口验收。普通游戏仍显示 legacy `player-opening-sheet`，不能在没有正式 Equipment Presentation 时把无武器身体设为默认。

### Phase 1.5：Weapon Socket Validation（仍属于 Phase 1）

Phase 1.5 不是新的正式武器阶段，也不增加玩法。它使用一个无伤害、无子弹、无升级入口的 dummy equipment，验证：

- grip/support 连接位置；
- 前臂与双手的组合位置；
- 装备 pivot 和 `+X` 朝向；
- 前后 depth/occlusion；
- rotation；
- body-only 动画播放时装备是否漂浮或穿入身体。

dummy equipment 只存在于显式开发预览，不能进入普通游戏。该验证未通过时，Phase 1 不能完成，也不能开始 Phase 2。

### Phase 2：武器存在感

目标：

- 接入独立手枪、霰弹枪和特斯拉设备；
- 武器方向独立于身体；
- 完成连接位置、前后遮挡、切换、换弹、暂停和重启；
- 枪口视觉与武器末端一致；
- 继续保持当前弹丸玩法起点。

本阶段使用独立武器门：

1. **Weapon Gate A**：手枪与人物连接、自动目标方向、前后遮挡和枪口视觉；
2. **Weapon Gate B**：霰弹枪重量、后坐、弹仓/换弹姿态，以及特斯拉放电端和链式方向；
3. **Weapon Gate C**：三种武器切换、暂停、受击、restart、fallback 和完整用户试玩。

只有 Weapon Gate C 获得项目所有者明确接受后，才允许把“body-only 人物 + 连接数据 + 正式武器组件”作为一个整体切换为普通游戏默认表现。身体和武器不能分两次上线。

### Phase 3：真实攻击来源与战斗反馈

目标：

- 经单独批准后迁移真实枪口；
- 对齐弹丸、电击、枪口和攻击结果；
- 完成后坐、曳光、命中和异常效果；
- 对受影响的局部玩法语义进行专项回归和用户试玩。

### Phase 4：异常光刃兼容验证

目标：

- 仅在显式开发模式启用自动光刃；
- 验证近战武器、作用范围、攻击轨迹和命中特效；
- 不进入正式游戏内容。

达到 Phase 4 不代表项目开始向主动动作游戏转型。

## 15. 生命周期、失败隔离与回退

所有表现对象必须遵守：

- 构造失败时销毁已经创建的全部对象；
- 销毁操作重复调用仍安全；
- 暂停时冻结自身表现，不影响玩法暂停；
- Scene restart 后不保留旧武器、动画、监听器、计时器或 tween；
- 表现异常不能阻止攻击、伤害、暂停、胜负或重启；
- 每次新一局重新创建表现控制器；
- 旧资源 fallback 永久保留。

正式 fallback 顺序为：

```text
完整 body-only + 连接数据 + 武器组件
→ legacy player-opening-sheet
→ player-rect
```

旧带枪 Gate 3 候选和 Gate 2 原型只作为历史证据保留，不进入新正式 fallback。

在 Weapon Gate C 接受之前，普通游戏默认停留在 legacy `player-opening-sheet`；上述完整分层组合只存在于显式开发预览。接受之后再一次性启用完整组合，并保留同一 fallback 顺序。

## 16. Player Feel Goals

Player Overhaul 的成功不是“新控制器能够运行”，而是玩家试玩后能稳定感受到：

1. 基金会干员不再是地图上滑动的图标，而是一个脚底明确、有重量、属于设施空间的单位。
2. 武器和异常设备不再只是伤害数值，而是角色实际携带、具有方向、重量和作用点的装备。
3. 自动攻击完全保留，但玩家能够看懂是谁在攻击、正在使用什么装备、攻击朝哪里发生。
4. 获得不同装备后，角色的战斗身份和视觉轮廓会发生可辨识变化，而不是只提高数值。
5. 所有表现增强都不能削弱走位、危险预警、敌人可读性或 Survivors 核心节奏。

单项特效更华丽、帧数更多或架构更复杂，都不能代替以上玩家感受。

## 17. 验收标准

### 17.1 玩法等价

除 Phase 3 明确批准的真实枪口变化外，以下结果必须保持：

- 移动速度和冲刺；
- 24×24 玩家碰撞体；
- 自动目标；
- 攻击频率；
- 弹丸数量、角度、速度、射程与穿透；
- 霰弹弹仓和换弹；
- 特斯拉目标顺序和衰减；
- 伤害、击杀、升级和奖励；
- 六分钟时间轴、Boss、胜负和存档。

表现控制器在缺失、正常、关闭或抛错时，玩法结果必须一致。

### 17.2 视觉验收

每阶段按当前适用范围必须包含：

- 原生 1× 素材检查；
- 960×540 真实游戏画面；
- 四方向移动和停止；
- 受击、冲刺、暂停和 restart；
- 正常资源和 fallback；
- console、缺失 key 和重复 key 检查；
- 用户亲自试玩。

Phase 2 起还必须包含：

- 身体与反方向武器组合；
- 手枪、霰弹枪和特斯拉；
- 武器切换、换弹/冷却和前后遮挡。

Phase 3 还必须检查真实枪口、弹道和攻击方向一致。

所有适用阶段必须确认：

- 无双武器；
- 无枪械残留在 body-only 人物中；
- 无漂浮、遮挡或跟随延迟；
- 脚底和阴影稳定；
- 武器与手臂连接自然；
- 新表现不遮挡危险预警。

### 17.3 自动验证

实施阶段需要与风险相称的：

- 角色、武器、攻击和 fallback 单元测试；
- 表现失败下的玩法等价测试；
- Scene lifecycle、pause 和多次 restart 测试；
- 全量 Node 测试；
- Python 素材工具测试；
- 生产构建；
- production bundle 开发入口泄漏检查；
- `git diff --check`；
- 最终 Git status；
- 新鲜浏览器 smoke。

自动测试通过不能代替真实尺寸视觉检查和用户试玩。

## 20. 主要风险与控制

### 风险 1：再次变成漂浮武器

控制：

- 使用手持前臂、双手和武器组合；
- 每帧记录连接位置；
- 不使用肩部偏移、回正延迟或漂浮跟随；
- 原生尺寸和真实游戏内检查。

### 风险 2：表现层改变玩法

控制：

- 玩法到表现的单向只读数据；
- 表现结果无返回值；
- 缺失、正常和抛错路径做结果等价对比；
- 真实枪口单独作为玩法门。

### 风险 3：一次生产大量错误素材

控制：

- Body Gate A/B/C；
- 单方向先行；
- 前一视觉门未接受时停止；
- 不一次生成所有身体、武器和异常装备。

### 风险 4：新旧冻结物混入

控制：

- 新隔离 worktree；
- 显式文件清单暂存；
- 每个 commit 前检查 staged list；
- 旧 UI/Art worktree 原样保留。

### 风险 5：未来近战反向绑架当前架构

控制：

- Phase 4 只验证兼容性；
- 不加入正式数值、升级和存档；
- 不让动画控制伤害；
- 产品化另行设计和批准。
